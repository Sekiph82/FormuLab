## Phase 4 architecture decisions
Reused every established Phase 1-3 pattern rather than inventing new ones: "unknown is contagious" (any finding with `humanReviewRequired: true` forces `unknown`, checked first in both `calculateClaimsReadiness` and `calculateLabelReadiness`, before any other check — unknown can never resolve to ready/supported by falling through other logic); supersession-via-self-referential-pointer (`supersedesClaimId`/`supersedesLabelId`/`supersedesArtworkId`, `derive*EffectiveStatus` scans siblings for a pointer back at the record in question); append-only-overlay-latest-wins for `LabelContentBlock` (key: labelId+labelRevision+blockType+language) and `ClaimEvidenceLink` (key: claimId+evidenceItemId, revoked excluded); authorization split identical to Phase 2/3 (`requireAuthorizedRegulatoryActor` for formal review/approve/reject/revoke, `requireHumanActor` for draft/propose actions, `system`/`import` actors blocked from both). Claim-vs-legislation and label-requirement rules reuse the EXISTING `RegulatoryRule.claimKeywordsAny`/`requiredLabelElements`/`requiredWarnings` fields rather than inventing a parallel rule concept — no new legislation is invented, only configured rules already in the regulatory engine are consulted, and seed rules remain marked unverified exactly as Phase 2 established.
Deliberate deviation from the suggested 10 Phase-4 collections: dropped `label_manual_actions` (the spec text never defined its fields anywhere, unlike every other collection) and added `claim_review_revocations` + kept `label_review_revocations` for full append-only-revocation symmetry with `ClaimReview`/`LabelReview`, matching the append-only-review-plus-revocation shape every other reviewed entity in the codebase already uses. Net: 9 collections, documented in both `claimsLabels.ts`'s header comment and `masterdata.rs`'s doc comment.
## Claims domain model
`packages/shared/src/schemas/claimsLabels.ts`: `productClaimSchema` — id/schemaVersion/claimCode/claimText/normalizedClaim/claimCategory (30 values)/formulationId/formulaVersionId/packagingSkuCode?/jurisdictions[]/languages[]/status (11 values)/riskLevel (low/medium/high/critical/unknown)/proposedBy/proposedAt/updatedBy/updatedAt/supersedesClaimId?. Bound to an exact formula version (no "current version" reference); packaging/jurisdiction/language scope explicit; a text revision creates a new record via `reviseClaim` rather than mutating; reviewed claims (`CLAIM_IMMUTABLE_STATUSES` = supported/supported_with_conditions/restricted/prohibited/rejected/superseded) reject further field mutation in `updateClaimStatus`/text edits; historical revisions stay readable via the supersession chain; `unknown` is a distinct risk/status value, never coerced to or treated as `supported`.
## Claims evidence model
`claimEvidenceLinkSchema` — id/schemaVersion/claimId/evidenceItemId/dossierId/dossierRevision/linkStatus (proposed/accepted/rejected/revoked)/linkedBy/linkedAt/reviewedBy?/reviewedAt?/notes?/revokesLinkId?. `proposeClaimEvidenceLink` (any human) creates `proposed`; `acceptClaimEvidenceLink`/`rejectClaimEvidenceLink` require `requireAuthorizedRegulatoryActor` and re-check eligibility (`evaluateClaimEvidenceEligibility` rejects expired/rejected/revoked/superseded evidence and any scope mismatch on formula version/jurisdiction/packaging SKU); `revokeClaimEvidenceLink` is append-only (new row with `revokesLinkId`, no mutation of the accepted row). `evaluateClaimEvidence` filters to `linkStatus === "accepted"` only — a fixed real bug where `activeLinksForClaim`'s general "not revoked" filter let a merely-proposed link incorrectly satisfy a claim.
## Label model
`productLabelSchema` — id/schemaVersion/labelCode/formulationId/formulaVersionId/packagingSkuCode/jurisdiction/language/status (10 values)/revision/createdBy/createdAt/updatedBy/updatedAt/supersedesLabelId?. `reviseLabel` creates a new revision rather than mutating; `LABEL_IMMUTABLE_STATUSES` blocks edits to approved/reviewed labels the same way claims are blocked.
## Artwork model
`labelArtworkSchema` — id/schemaVersion/labelId/labelRevision/artworkCode/attachmentIds/format/dimensions/colorMode/languageSet/createdBy/createdAt/status (7 values)/supersedesArtworkId?. `uploadArtwork` (human) starts draft/pending; `approveArtwork`/`rejectArtwork` require `requireAuthorizedRegulatoryActor`; `replaceArtwork` creates a new artwork row pointing `supersedesArtworkId` at the old one, which makes any prior artwork review stale per `evaluateArtworkReadiness`.
## Market and language rules
`LABEL_UI_LANGUAGES = ["en","tr","sw"]` (English/Turkish/Swahili minimum, per spec §13). `LABEL_TRANSLATION_STATUSES` = draft/machine_suggested/human_review_required/reviewed/rejected/superseded — `machine_suggested` can never be treated as `reviewed`; no automatic-translation-as-regulatory-review path exists anywhere in the engine.
## Claims review workflow
`claimReviewSchema` — id/schemaVersion/claimId/claimRevision/formulationId/formulaVersionId/packagingSkuCode?/jurisdiction/language/reviewedBy/reviewerRole/reviewedAt/outcome (6 values)/conditions?/notes?/evidenceSnapshot/ruleSnapshot/revokesReviewId? (added beyond the spec's own §9.3 field list, for consistency with every other reviewed-entity type in the codebase, including the spec's own `LabelReview` two sections later). `recordClaimReview`/`revokeClaimReview` both `requireAuthorizedRegulatoryActor`; review is bound to the exact claim revision + formula version + jurisdiction + language (cannot cross packaging SKUs per spec); snapshots are frozen at review time and never recomputed; revocation is append-only via `claimReviewRevocationSchema`, never a mutation of the original review.
## Label review workflow
`labelReviewSchema` — id/schemaVersion/labelId/labelRevision/artworkId/artworkRevision/formulaVersionId/packagingSkuCode/jurisdiction/language/reviewedBy/reviewerRole/reviewedAt/outcome (5 values)/findingsSnapshot/contentSnapshot/claimsSnapshot/notes/revokesReviewId?. Same append-only-plus-revocation shape as claim reviews; bound to an exact label AND artwork revision — a new artwork revision makes the review stale, exactly as a new label content revision does (`compareLabelRequirementsToCurrentRules`/`evaluateFormulaLabelConsistency` surface staleness rather than silently treating an old review as still valid).
## Formula-to-label consistency
`evaluateFormulaLabelConsistency` compares: product name, formula version reference, packaging SKU, net quantity, ingredient declaration + INCI order (against the exact saved formula version — never a "current"/working draft), warnings derived from safety findings, storage, expiry, directions. `evaluateClaimLabelConsistency` separately compares claims printed on the label against claims that actually hold a `supported`/`supported_with_conditions` review outcome, flagging any prohibited claim present on the label and any restricted claim missing its required conditions text. A working (unsaved) formula version can never be the basis for an approved label — `resolveLabelRequirements`/`evaluateFormulaLabelConsistency` both take a saved `formulaVersionId`, there is no "current draft" input path.

## Bug found during live verification (10th, discovered after the "Bugs discovered" section above was written)
**Symptom**: in the live app, clicking "Accept" on a proposed claim-evidence link always failed with `claim_evidence_links record claimevidencelink-<id> already exists. This collection is append-only...`, and the link stayed `proposed` forever — confirmed via the Audit tab, which showed only a `claim.evidence_link_proposed` event, never an `accepted` one, across three retries.
**Root cause**: `acceptClaimEvidenceLink`/`rejectClaimEvidenceLink` in `packages/shared/src/engine/claims.ts` did `{ ...link, linkStatus: "accepted", ... }` — spreading the existing link and keeping its `id`. Since `claim_evidence_links` is registered append-only (overlay-latest-wins by `(claimId, evidenceItemId)`, same pattern as `regulatory_requirement_evidence_links`), every accept/reject attempt tried to insert a row with an `id` that already existed (the just-created `proposed` row), and the append-only guard correctly refused it. `revokeClaimEvidenceLink` in the same file already did this right (`id: newId("claimevidencelink")`), and the equivalent dossier-side functions (`acceptEvidenceLink`/`rejectEvidenceLink` in `regulatoryDossier.ts`) already mint a fresh id on every transition — this was an inconsistency introduced only in the claims-evidence-link code, not a design gap.
**Fix**: added `id: newId("claimevidencelink")` to both `acceptClaimEvidenceLink` and `rejectClaimEvidenceLink`, matching the working `revokeClaimEvidenceLink`/dossier pattern exactly. `activeLinksForClaim` groups by `evidenceItemId` (not `id`), so this does not change any grouping/overlay logic — verified by re-running the full `claims.test.ts` (28/28) and the full shared (852/852) and desktop (451/451) suites, all clean, no regressions. Committed as `8ae30a6`, pushed to `origin/feature/laboratory-stability`.
**Live re-verification**: could not be re-tested against the *already-running* app instance (it was built from source before the fix and only reads compiled JS), so re-verification is deferred to after the release rebuild in this same session — see "Native verification" below for the outcome.
