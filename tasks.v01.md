# Supplier Document Intelligence and Reference Formulation Intelligence — V01 Task Plan

## Goal and scope

FormuLab should connect to supplier systems that a customer is authorized to use, discover the accessible product catalog, acquire available product data and documents, report coverage and gaps, and support repeatable synchronization. Each supplier and access surface has its own adapter and capability profile.

“All products” means all products exposed to the connected account for the configured supplier surface, market, language, product line, and authorization. The system must report the scope it actually covered and must not imply access to products or documents that were unavailable. Automated access is permitted only where the supplier's terms and the customer's authorization allow it. Otherwise, use user-attended or manual-assisted workflows.

Acquired documents and extracted values are evidence-backed source records. TDS/SDS values are proposals and must never silently overwrite `RawMaterial`. Applying a value to a master record requires field-level review and an explicit authorized user action.

### Existing FormuLab foundation that V01 MUST reuse

V01 does **not** rebuild the connector/data-exchange foundation already completed in FVL-04. The existing production authorities include the `SourceConnector` contract, generic FILE connector, REST API connector, schema discovery, versioned mapping profiles, external-ID crosswalks, deterministic transformations, incremental re-import/conflict handling, and the Connector -> existing Data Exchange bridge. V01 extends those authorities for supplier-specific acquisition and document intelligence; it must not create a parallel connector framework, mapping engine, crosswalk registry, Data Exchange platform, Material Master, or approval system.

Existing FVL-04 material-document support is metadata-oriented. V01 adds acquired binary document storage, parser/extraction records, supplier-specific discovery, commercial-product identity resolution, supplier-formulation ingestion, and reference-formulation intelligence while preserving backward compatibility.

TDS is optional evidence, not a prerequisite for the SDS-first path. When TDS is unavailable, FormuLab must resolve only what the SDS and other authorized evidence support, retain uncertainty, and never infer an undisclosed composition or unsupported active matter.

## Milestone SDM-00 — Research and scope definition

- **SDM-00.001 — Define customer workflows:** Specify single-product lookup, bulk catalog discovery, first connection, recurring synchronization, and manual document import. Acceptance: user roles, tenant/customer boundary, and workflows are explicit.
- **SDM-00.002 — Define “full catalog” coverage:** Scope products, documents, and fields by provider account, surface, market, language, product line, and user entitlement. Acceptance: completeness claims are tied to a measurable scope; inaccessible or unknown scope is reported as a gap.
- **SDM-00.003 — Classify access methods:** Define official APIs, bulk feeds/downloads, public search, user-attended portal sessions, and manual import. Acceptance: a surface with unverified automation permission is not marked READY for automated acquisition.
- **SDM-00.004 — Build supplier/surface coverage matrix:** Research CHT, Nouryon, Clariant, Dow, DyStar, Archroma, BASF, Evonik, and Croda by surface, market, language, product line, document type, authentication, and research status. Acceptance: every entry has evidence and an observation date; unknowns remain explicitly unknown.
- **SDM-00.005 — Review terms and authorization:** Verify API terms, portal conditions, rate limits, download/reuse rights, and retention limits for each surface. Acceptance: unverified access paths are excluded from automated acquisition.
- **SDM-00.006 — Define product identity vocabulary:** Model supplier code, trade name, grade, product family, CAS/EC, INCI, customer SKU, market, and language variants. Acceptance: CAS alone cannot establish a product/grade match; conflicting aliases require review.
- **SDM-00.007 — Define product-data and document taxonomy:** Separate product-profile fields from SDS, TDS/PDS, COA, specification, regulatory declaration, and certificate records. Acceptance: source document type and source field name are retained alongside normalized classifications.
- **SDM-00.008 — Define Document Intelligence boundaries:** Specify extractable TDS/SDS fields and decisions requiring authorized review. Acceptance: every extracted field is a source-linked proposal and cannot automatically modify `RawMaterial`.
- **SDM-00.009 — Define representative fixtures and rights:** Select authorized, reusable supplier-formulation PDFs plus SDS/TDS/COA/certificate examples by product, market, language, revision, and PDF type. Acceptance: fixture identity, source, and use/retention conditions are known.
- **SDM-00.010 — Define coverage and quality metrics:** Measure catalog pagination, product matching, document discovery, file acquisition, and extraction separately. Acceptance: completion reports include scanned scope and gaps, not merely a successful job status.

## Milestone SDM-01 — Shared domain, connections, and secure storage

- **SDM-01.001 — Architecture RFC:** Design provider registry, connections, surfaces, catalog discovery, acquisition jobs, immutable documents, extraction, and review. Acceptance: data flow, failure boundaries, tenant/authorization boundaries, and offline behavior are documented.
- **SDM-01.002 — Provider, surface, and account model:** Represent supplier, search/portal surface, and customer account connection as distinct entities. Acceptance: CHT public content and myCHT are separate capabilities and authorization profiles under one provider.

- **SDM-01.004 — Extend the existing FVL-04 connector contract with supplier-document capabilities:** Reuse the canonical `SourceConnector`/REST/file/data-exchange authorities and add only supplier-specific product search/listing, pagination, document discovery/fetch, authentication, coverage, and limitation capabilities that are missing. Acceptance: no second connector framework is created; adapters explicitly return unsupported capabilities.
- **SDM-01.005 — Product catalog snapshot model:** Store source product identity, normalized match candidates, source fields, discovery time, and catalog snapshot. Acceptance: source supplier names/codes remain preserved beside normalized values.
- **SDM-01.006 — Product/document revision model:** Separate product-page revision, document revision, and acquisition time. Acceptance: new documents never replace old blobs; revision lineage can use a `supersedes` relation.
- **SDM-01.007 — Job state machine and checkpoints:** Track discovery, pagination, download, and extraction with resumable checkpoints. Acceptance: interrupted jobs resume and retries do not duplicate products/documents.
- **SDM-01.008 — Large-catalog job management:** Support cancellation, resumption, throttling, and partial results for long catalog scans. Acceptance: one provider failure does not discard another provider's results.
- **SDM-01.009 — Credential/session security:** Use OS credential-manager/keychain references and user-attended authentication. Acceptance: secrets never enter job payloads, logs, exports, or crash reports; users complete MFA/CAPTCHA themselves.
- **SDM-01.010 — Network and file security:** Enforce allowed hosts, HTTPS, redirect validation, SSRF/IP defenses, size/time limits, MIME/signature checks, and safe filenames. Acceptance: local-network redirects, path traversal, and content-type mismatches are safely rejected.
- **SDM-01.011 — Immutable document store:** Address document blobs by content hash and store original filename, URL, acquisition time, and provider metadata separately. Acceptance: repeated acquisition of identical content avoids redundant binary copies while preserving source provenance.
- **SDM-01.012 — Backward-compatible FormuLab linkage:** Add compatible links from existing `material_documents` and material relationships to blobs and extraction records. Acceptance: existing metadata remains readable; import creates no material, verification, or approval automatically.
- **SDM-01.013 — Audit and provenance model:** Record initiating user, provider/surface, scope, query/snapshot, URL, hash, adapter/parser version, and review decisions. Acceptance: the source of a product or extraction can be reconstructed end to end.
- **SDM-01.014 — Retention, deletion, and export model:** Define lifecycle and retention relationships for documents, extractions, connections, and audit records. Acceptance: document deletion behavior and audit preservation are explicit.

## Milestone SDM-03 — Document Intelligence and controlled extraction

- **SDM-03.001 — File admission and quarantine:** Check MIME/signature, size, page count, encryption, malformed PDFs, and risky files. Acceptance: rejected files do not enter processing and have a recorded reason.
- **SDM-03.002 — Reproducible PDF text extraction:** Preserve page boundaries and text coordinates. Acceptance: text artifacts can be reproduced from document hash and parser version.
- **SDM-03.003 — OCR evaluation:** Compare offline OCR candidates on supported languages and representative supplier PDFs. Acceptance: accuracy, speed, package size, and offline requirements are decided by language.
- **SDM-03.004 — Conditional OCR pipeline:** Run OCR only on pages with insufficient text layers. Acceptance: OCR-derived text and uncertainty are explicitly labeled.
- **SDM-03.005 — SDS section parser:** Identify SDS sections across languages and layouts. Acceptance: sections 1–16 are measured; a missing section is not interpreted as a negative fact.
- **SDM-03.006 — SDS identity/composition extraction:** Extract CAS/EC, substance name, composition ranges, and Section 3 data. Acceptance: partial disclosure is preserved; an undisclosed component is not treated as absent.
- **SDM-03.007 — SDS hazard/GHS extraction:** Extract class/category, signal word, pictograms, and H/P statements. Acceptance: no classification is invented; market/regulatory context and evidence page are retained.
- **SDM-03.008 — SDS operational safety extraction:** Extract handling, storage, exposure controls, PPE, transport, and regulatory sections. Acceptance: extracted values do not create safety decisions or approvals.
- **SDM-03.009 — TDS/PDS field extraction:** Extract active matter, density, pH, viscosity, ionic character, appearance, recommended dosage, storage, shelf life, and application guidance. Acceptance: typical value, min/max, specification limit, and recommendation remain distinct.
- **SDM-03.010 — TDS measurement context:** Associate temperature, method, concentration, conditions, and units with each value. Acceptance: context-free pH/viscosity and similar fields are not presented as unconditional properties.
- **SDM-03.011 — Other document extraction:** Extract COA, specification, certificate, and regulatory declaration fields such as lot, limit, measurement, scope, issuer, and validity dates. Acceptance: COA lot values do not enter general master fields; certificate scope is linked to product/site.
- **SDM-03.012 — Field-level provenance:** Store source hash, revision, page/section, evidence text, parser/OCR version, confidence, and normalization steps per extraction. Acceptance: users can inspect the evidence for each value.
- **SDM-03.013 — Original and normalized value model:** Preserve source text/unit separately from normalized value/unit. Acceptance: conversions and rounding are traceable and the original expression remains available.
- **SDM-03.014 — Confidence and review thresholds:** Set field- and document-risk-specific thresholds. Acceptance: field-level review replaces a single aggregate score; critical safety fields cannot be auto-accepted at low confidence.
- **SDM-03.015 — Conflict and uncertainty handling:** Handle conflicting documents, unreadable fields, unknown units, and uncertain product matches. Acceptance: unknown remains unknown and the system does not fabricate values.
- **SDM-03.016 — Product/grade resolution:** Generate match candidates from supplier codes, grades, aliases, CAS, and regional variants. Acceptance: ambiguous or conflicting matches cannot automatically link to a material.
- **SDM-03.017 — Document revision comparison:** Detect revisions by hash, publication date, revision number, and content changes. Acceptance: prior extractions remain preserved and new values do not overwrite them.
- **SDM-03.018 — Evaluation set and quality measurement:** Measure SDS/TDS fields across languages, scanned/digital PDFs, and supplier layouts. Acceptance: field-level precision/recall and human-review rates are reported.

## Milestone SDM-06 — Supplier formulation PDF ingestion and structured reference formulas

- **SDM-06.003 — Conditional formulation OCR fallback:** Reuse the SDM-03 PDF/OCR pipeline when a formulation PDF lacks a usable text layer. Acceptance: OCR is bounded, page-scoped, and explicitly labeled; digital-text PDFs never incur unnecessary OCR.
- **SDM-06.004 — Formulation identity extraction:** Extract supplier/manufacturer, product family/application title, source formulation code, publication/revision/date, document title, market/language when present, and source page. Acceptance: absent identity fields remain unknown rather than inferred from filenames alone.
- **SDM-06.005 — Formula-line extraction:** Extract original ingredient/trade name, supplier product code where present, INCI/chemical wording if present, function, phase/order where present, original amount, unit/basis, q.s. semantics, and source evidence. - **SDM-06.006 — Process/procedure extraction:** Extract ordered addition steps, dissolving/mixing instructions, pH-adjustment instructions, temperature, mixing time/speed, hold, clarity/homogeneity instructions, and other explicit process facts. - **SDM-06.007 — Finished-product target extraction:** Extract explicit pH, viscosity, density, appearance, and other formula-level targets/results with units and context. Acceptance: approximate values stay approximate and are not promoted to specifications.
- **SDM-06.008 — Formula arithmetic and basis validation:** Validate totals, units, q.s. behavior, duplicate lines, and parse consistency without silently fixing source errors. Acceptance: source totals and computed totals are both retained when they disagree.
- **SDM-06.009 — Source ingredient identity candidates:** For each supplier-specific line, generate candidate links to acquired commercial-product records using exact supplier + trade name/product code first, then controlled aliases. - **SDM-06.010 — Missing-document state:** Mark formulation ingredients with no matching SDS/TDS/product evidence as unresolved and queue them for acquisition/manual upload. Acceptance: the formula can still be stored as reference evidence but unresolved lines cannot masquerade as canonical chemistry.
- **SDM-06.011 — Reference-formulation canonical record:** Persist a structured, queryable reference formula separate from production `Formulation`/`FormulationVersion`. Acceptance: importing a supplier reference does not create a validated FormuLab production formula, lab result, approval, or measured-performance claim.

- **SDM-06.014 — Formulation extraction review UI:** Show original PDF/page evidence beside extracted identity, lines, process, targets, and unresolved product links. Acceptance: users can accept/edit/reject extracted fields without editing the immutable source artifact.

## Milestone SDM-07 — Commercial product identity and canonical chemical resolution

- **SDM-07.001 — Commercial product identity model:** Create a supplier-specific commercial-product record preserving manufacturer, trade name, supplier product code/grade, market/language variants, source documents, and aliases. Acceptance: supplier product identity is never collapsed into a canonical chemical record.
- **SDM-07.002 — Canonical chemical vocabulary/library:** Define stable canonical chemical/family identities with CAS/EC, accepted names, abbreviations, INCI where appropriate, chemical family, and FormuLab function tags. Acceptance: aliases resolve to stable IDs; supplier trade names are not canonical IDs.
- **SDM-07.003 — CAS/EC/name normalization:** Normalize punctuation, CAS/EC formatting, known synonyms/abbreviations, and source names deterministically while retaining originals. Acceptance: normalization never merges conflicting identifiers silently.
- **SDM-07.004 — SDS Section 1 identity resolver:** Use supplier/product/chemical-name declarations from Section 1 as explicit evidence separate from Section 3 composition. Acceptance: a declared commercial concentration such as “30% in aqueous solution” is stored as its own evidence claim, not conflated with a Section 3 hazard-disclosure range.
- **SDM-07.005 — SDS Section 3 component model:** Persist each disclosed component with original chemical name, CAS/EC, concentration expression/range, trade-secret flag, page/section evidence, and normalization result. Acceptance: undisclosed remainder stays unknown.
- **SDM-07.006 — Single-component resolver:** Resolve products whose evidence supports one dominant canonical chemical to that chemical with an evidence-backed relationship and confidence state. Acceptance: exact/near-pure evidence may yield high confidence; no supplier name heuristic is sufficient by itself.
- **SDM-07.007 — Multi-component/blend resolver:** Represent commercial blends as ordered/set component evidence plus known concentration ranges and unresolved remainder. Acceptance: blends are never flattened into a false single canonical chemical.
- **SDM-07.008 — Proprietary/partial disclosure handling:** Preserve TSC/trade-secret, withheld identity/range, generic chemical-family wording, and unknown remainder. Acceptance: result becomes `PARTIAL`, `AMBIGUOUS`, or `UNKNOWN` as appropriate rather than fabricated.
- **SDM-07.009 — Confidence state model:** Implement `EXACT`, `HIGH_CONFIDENCE`, `PARTIAL`, `AMBIGUOUS`, and `UNKNOWN` with machine-readable reasons and evidence references. Acceptance: confidence is rule/evidence-derived and reviewable, not an unexplained scalar.
- **SDM-07.010 — Composition fraction vs active matter distinction:** Store SDS disclosed composition fraction separately from supplier-declared active matter/solids. Acceptance: a Section 3 hazardous-component range is never automatically called active matter.
- **SDM-07.011 — Bounded active-content derivation:** Derive active content only from explicit source evidence that actually states active concentration or an equivalent defensible basis. Acceptance: formula-level active contribution may be calculated as a value or range with lineage; otherwise it remains unavailable.
- **SDM-07.012 — Physical-property evidence:** Preserve SDS Section 9 pH, relative density/density, viscosity, solubility, appearance, and measurement context as proposed evidence. Acceptance: e.g. pH measured at 5% or 10% remains condition-bound and never becomes unconditional master pH.
- **SDM-07.013 — Human identity review:** Provide accept/edit/reject/needs-review workflow for commercial-product -> canonical-chemical/component relationships and field-level evidence. Acceptance: no automatic `RawMaterial` overwrite or material verification.
- **SDM-07.014 — Canonical material application proposal:** After human acceptance, generate field-level proposals against existing RawMaterial records/crosswalks through the existing Data Exchange/material workflow. Acceptance: explicit user action remains the only master-data write gate.
- **SDM-07.015 — Croda Incromine fixture:** Resolve the supplied Incromine Oxide C evidence as a Croda commercial product with Section 1 chemical-name evidence “Cocamidopropyl Dimethylamine Oxide (30% in Aqueous Solution)” while separately preserving Section 3 CAS 68155-09-9 / 15-40% trade-secret disclosure and Section 9 context. Acceptance: no false claim that the Section 3 range itself equals exact active matter.
- **SDM-07.016 — Croda ECO Brij L6L fixture:** Resolve the supplied product to ethoxylated alcohol CAS 68439-50-9 with the SDS-declared 90-100% composition range and preserve Section 9 evidence. Acceptance: high-confidence canonical family resolution does not invent an ethoxylation number or narrower composition than stated.
- **SDM-07.017 — Croda NatraSense AG-810 fixture:** Resolve D-glucopyranose oligomeric decyl/octyl glycosides CAS 68515-73-1 with the SDS-declared 65-75% range and preserve pH/relative-density/viscosity contexts. Acceptance: canonical APG-family classification is evidence-backed and original trade identity remains intact.
- **SDM-07.018 — Croda Crodateric CDA 38 fixture:** Preserve the product as a Croda commercial blend/product whose SDS discloses an imidazole compound CAS 68608-65-1 at 30-60% with trade-secret limitations. Acceptance: formulation function “hydrotrope/stabilizer” is retained as supplier-formulation evidence but does not justify inventing undisclosed composition.

## Milestone RFI-01 — Reference formulation normalization and corpus ingestion

- **RFI-01.001 — Original-vs-normalized dual representation:** Store each reference formula line with immutable original supplier text/amount/function plus separately versioned normalized commercial-product/canonical-chemistry links. Acceptance: normalization can improve without rewriting the supplier source.
- **RFI-01.002 — Supplier-product crosswalk reuse:** Reuse/extend FVL-04 external-ID crosswalk concepts for supplier product codes/trade names -> commercial product IDs where semantically appropriate. Acceptance: do not create a second generic crosswalk authority; formula-specific mapping evidence remains distinguishable.
- **RFI-01.003 — Normalized formula contribution model:** Calculate canonical component contributions only where product composition evidence supports them, preserving ranges and unknown remainder. Acceptance: `supplier product % x component fraction` produces bounded lineage-backed contributions, not false point estimates.
- **RFI-01.004 — Ingredient-function evidence separation:** Preserve the supplier formula's stated functionality separately from FormuLab canonical material functions. Acceptance: supplier-described “hydrotrope/stabilizer” or “nonionic detergent” is evidence, not automatic canonical truth.
- **RFI-01.005 — Formula/process/target indexing schema:** Build query-optimized records for product family, ingredient/commercial product/canonical chemical, amount/range, phase/order, functions, process facts, pH/viscosity/other targets, supplier, region, and source revision. Acceptance: generator/retrieval paths never need to parse the original PDF at runtime.
- **RFI-01.006 — Search/index build:** Create deterministic local indexes for ingredient aliases, canonical chemical IDs, commercial product IDs, product families, functions, supplier, and numeric dosage/target ranges. Acceptance: indexes are rebuildable from immutable normalized records and contain no hidden source of truth.
- **RFI-01.007 — Bulk supplier-formula import job:** Support hundreds/thousands of authorized formulation PDFs with resumable parsing, deduplication by source hash/identity, partial failures, and review queues. Acceptance: one bad PDF does not block the corpus and re-import does not duplicate accepted records.
- **RFI-01.008 — 2,000-formula corpus readiness:** Define corpus quality metrics by product family, supplier, resolved-line coverage, unresolved-line coverage, source revision, and parser confidence before using the corpus for generation. Acceptance: raw formula count alone is never treated as corpus quality.
- **RFI-01.009 — Supplier-bias metadata:** Record supplier concentration by family and ingredient/commercial-product dominance. Acceptance: one supplier's portfolio cannot silently define universal formulation priors.
- **RFI-01.010 — Licensing/use-rights metadata:** Attach source-use/retention/reuse constraints to corpus records. Acceptance: restricted portal material can be excluded from derivative/export use according to recorded rights.
- **RFI-01.011 — Corpus review UI:** Show source formula, normalized lines, unresolved products, evidence links, active/contribution ranges, and review state. Acceptance: reviewers can trace every normalized fact to source formula/SDS evidence.
- **RFI-01.012 — Corpus backup/restore:** Preserve source identities, hashes, commercial-product mappings, canonical links, extracted evidence, reviews, and indexes/rebuild metadata. Acceptance: restore does not silently retarget mappings to newer supplier documents.

## Milestone RFI-02 — Reference formulation intelligence and generator integration

- **RFI-02.001 — Product-family priors:** Compute ingredient/canonical-chemical frequency and dosage distributions per product family from reviewed normalized formulas only. Acceptance: sample counts and supplier composition are reported with every prior.
- **RFI-02.002 — Co-occurrence intelligence:** Compute reviewed ingredient/function/component co-occurrence patterns without treating correlation as chemical compatibility proof. Acceptance: co-occurrence is advisory evidence only.
- **RFI-02.003 — Process-pattern intelligence:** Derive addition-order, phase, pH-adjustment, thickening, temperature, mixing, and finish-pattern statistics where explicitly present. Acceptance: missing process details remain missing and never imply a default.
- **RFI-02.004 — Active/contribution distributions:** Compute component/active contribution distributions only from formulas with defensible composition/active evidence. Acceptance: formulas with unresolved commercial products are excluded from that statistic or represented as bounded uncertainty.
- **RFI-02.005 — Similarity and nearest-reference retrieval:** Retrieve reference formulas by product family, canonical chemistry, function vector, dosage ranges, process/target context, market, and supplier-neutral features. Acceptance: retrieval returns source references and distances; it never labels similarity as validation.
- **RFI-02.006 — Supplier-neutral prior aggregation:** Weight/report priors so a dominant supplier cannot silently become the universal baseline. Acceptance: per-supplier and pooled statistics are inspectable and sample-size aware.
- **RFI-02.007 — Generator candidate context adapter:** Expose reviewed reference priors and nearest-reference evidence to the existing deterministic formulation generator without bypassing current hard rules. Acceptance: generator remains deterministic/zero-LLM capable.
- **RFI-02.008 — Hard-gate precedence:** Preserve Safety, Regulatory, compatibility/manufacturing feasibility, material availability, and explicit technical constraints as authoritative gates over reference popularity. Acceptance: a common supplier pattern cannot override a hard FAIL.
- **RFI-02.009 — Reference evidence in ranking/explainability:** Show when a generated candidate is supported by dosage priors, co-occurrence, or similar supplier references, including corpus counts and source links. Acceptance: reference evidence stays distinct from model prediction and measured validation.
- **RFI-02.010 — No-validation invariant:** Enforce `supplier reference formula != measured validation`, `SDS evidence != performance proof`, and `supplier recommendation != validated result` across schemas, UI, ranking, exports, and audit. Acceptance: only real LaboratoryTrial/TestResult evidence can satisfy measured-validation semantics.
- **RFI-02.011 — Holdout/reference leakage controls:** When evaluating generation quality against the reference corpus, prevent the exact evaluated formula or near-duplicate revisions from serving as retrieval evidence for itself. Acceptance: acceptance metrics distinguish memorization from useful generalization.
- **RFI-02.012 — Multi-supplier realism acceptance:** Evaluate generated formulas against held-out reviewed references from at least three genuinely different suppliers/product families using structural/dosage/process plausibility metrics plus chemist review. Acceptance: no claim of laboratory performance is made from reference similarity alone.
- **RFI-02.013 — Croda end-to-end acceptance:** Starting from the supplied HC/DW/22 PDF and four supplied SDS files, prove source ingestion -> formula extraction -> commercial-product matching -> SDS composition evidence -> normalized/indexed reference formula -> retrieval-ready record, while leaving SLE(3)S/Crothix or any unsupported identity unresolved until evidence exists.
- **RFI-02.014 — Generator integration acceptance:** Generate a candidate using the existing FormuLab engine with reference intelligence enabled and disabled, prove deterministic hard-gate equivalence, show reference-driven explainability differences, and verify no source/reference record is mutated.

## Completion criteria

For supported suppliers, a customer can connect through an authorized surface, scan the exposed catalog, acquire permitted product data, formulation PDFs and documents, and see coverage and gaps. FormuLab extracts SDS/TDS/document fields as evidence-backed proposals, parses supplier formulations into immutable structured reference records, resolves supplier commercial products to canonical chemistry only to the extent supported by evidence, and builds queryable normalized/indexed records so generation never needs to parse source PDFs at runtime. The same pattern extends across independently verified supplier surfaces and layouts.

“Connected” alone is not success. FormuLab must report which products and documents it saw, under what scope, which it acquired, which fields it extracted, and which decisions still require a human.
