## Phase 3 design decisions
- **8 persistence collections instead of the suggested 10** — trimmed `regulatory_evidence_revisions` (evidence supersession uses a self-referential `supersedesEvidenceId` chain on the same mutable `regulatory_evidence_items` collection, exactly the pattern `RegulatoryRule` already uses; a separate revisions collection would duplicate what the chain already gives for free) and made `regulatory_dossier_submissions` a mutable tracking row rather than append-only-per-status-change (it's an internal log, not a compliance-critical evidence record, and the global audit log already covers its history).
- `RegulatoryDossierRequirement` rows are append-only per `(dossierId, dossierRevision, requirementCode)` — a manual exclusion never mutates the original row, it appends a new one with `status: "excluded"`; `currentRequirementsForRevision` takes the latest row per code. This keeps "frozen when the revision is created" literally true while still allowing exclusion within a draft revision.
- Authorization split per spec §12's literal action list: `requireAuthorizedRegulatoryActor` (regulatory/quality/administrator) gates verify/reject/revoke evidence, manual add/exclude requirement, dossier review record/revoke, submission record/status-update. A new, lighter `requireHumanActor` (any human role, still never AI/system/import) gates dossier creation/revision, draft evidence upload/replacement, and propose/accept/reject/revoke of a requirement-evidence *link* — accepting a link is explicitly "a human must accept the mapping" in spec §4.4, not narrowed to the three authorized roles the way formal *evidence* verification is.
- `dossierApprovalSnapshotSchema` lives in `schemas/dossier.ts`, not `schemas/formulation.ts` — avoids re-creating the exact `formulation.ts`↔`regulatory.ts`-style import cycle risk fixed earlier this session; `formulation.ts`'s `ApprovalRecord.dossierSnapshot` field references this type via a value import of `dossier.ts` only (one direction, no cycle, verified by typecheck).

## Automatic record discovery (spec §7)
New file `packages/shared/src/engine/dossierRecordDiscovery.ts` (~230 lines) + `dossierRecordDiscovery.test.ts` (9 tests). `discoverDossierEvidenceCandidates(ctx)` is a pure, read-only function returning `DossierEvidenceCandidate[]` — suggestions only, never persisted by this function itself. Covers 6 of the sources spec §7 lists: raw-material documents (SDS/COA/TDS/spec/certificate — only for materials actually used in the target formula version's lines), laboratory trial test-result attachments, stability study result attachments, packaging compatibility snapshots (no attachment — references the computed findings), regulatory reviews, and Phase 2 regulatory evidence confirmations. Each candidate carries `matchesFormulaVersion`/`matchesPackagingSku`/`matchesJurisdiction` flags that are computed but never used to filter a candidate out — a version/SKU/jurisdiction mismatch stays visible rather than being silently hidden, per spec's explicit "wrong version/jurisdiction/packaging must be shown."

Deliberately NOT covered, documented in the file's own header comment rather than silently omitted: supplier/`MaterialSupplier` and packaging (`PackagingBom`/`PackagingComponent`) records have no document/attachment field in their current schema — adding one is a schema change out of scope for "wiring discovery," so supplier declarations and artwork remain manually-added-only for now. `CostSnapshot` isn't documentary evidence. `ApprovalRecord` is deliberately excluded to avoid a circular reference (an approval can itself depend on this same dossier via `regulatoryDossierApproval.ts`).

`candidateToDraftEvidenceInput(candidate, dossier)` turns an accepted suggestion into `AddDraftEvidenceInput` with `sourceType: "formulab_record"` and `sourceEntityId` set to the originating record's id — `addDraftEvidence` itself still requires a human actor and starts the item unverified, so accepting a suggestion is never itself a verification. Attachments are carried forward BY REFERENCE (same `id`/`location` as the source record's own `AttachmentReference`, or a synthesized reference for `RawMaterial.documents`, whose shape differs from `attachmentReferenceSchema`) — never copied as new files.
